# 性能测试规划（后续版本执行）

## 1. 目标

验证系统在并发预约场景下的正确性与容量，重点暴露「同一时段并发创建」是否会产生重复占用，
以及高频读接口在预期负载下的响应表现。本规划先落文档，压测脚本与执行放在后续版本。

## 2. 压测范围（按优先级）

| 优先级 | 接口 | 关注点 |
|--------|------|--------|
| P0 | `POST /api/meeting/reservation/create` | 并发冲突检测是否会出现同房间同时段重复预约 |
| P1 | `GET /api/meeting/reservation/schedule`、`GET /api/meeting/room/list` | 日历/列表查询 TPS 与 P95 |
| P1 | `POST /api/auth/login` | 登录 TPS、Redis Token 写入压力 |
| P2 | `GET /api/meeting/home/stats` | 聚合统计查询耗时 |

## 3. 环境与数据准备

- 复用 docker-compose 基础设施：MySQL、Redis、Nacos、RocketMQ，各服务独立部署。
- 数据种子：至少 200 用户、20 会议室、多个部门；预置跨多天的历史预约数据，使 schedule/stats 查询更贴近真实。
- 与生产隔离：使用独立测试库/实例，避免污染开发与线上数据。

## 4. 工具与观测

- 压测工具：JMeter（推荐）或 Gatling；并发场景优先用同步请求验证正确性，再用高并发测吞吐。
- 观测：Prometheus + Grafana（或 JVM/Redis/MySQL 指标面板），重点看连接池、GC、慢查询、Redis QPS。
- 正确性断言：压测结束后检查数据库中是否出现「同房间 + 时间段重叠 + 状态非取消/拒绝」的重复记录。

## 5. 场景与指标

| 场景 | 并发/时长 | 通过标准（建议） |
|------|-----------|------------------|
| 预约创建-同房间同时段 | 50 线程 x 1 分钟 | 0 重复占用；错误率 < 0.1% |
| 预约创建-混合房间 | 100 线程 x 5 分钟 | P95 < 500ms；错误率 < 0.5% |
| 日程/列表读 | 200 线程 x 5 分钟 | P95 < 300ms |
| 登录 | 100 线程 x 3 分钟 | P95 < 300ms |
| 首页统计 | 100 线程 x 3 分钟 | P95 < 500ms |

> 阈值需在拿到当前硬件/部署形态基线后校准，上表为首版参考值。

## 6. 执行阶段

1. 先修完 #4 的并发冲突原子性（数据库唯一约束或分布式锁），否则 P0 压测必然暴露重复占用，脚本会持续失败。
2. 搭建观测与数据准备脚本，跑一轮小并发冒烟，确认环境无瓶颈。
3. 按上表逐场景执行，记录 TPS / RT 分位 / 错误率 / 资源水位。
4. 输出报告：瓶颈定位（慢 SQL、连接池、网关、Redis）+ 优化项，回填到 `.harness/changes/` 对应变更记录。

## 7. 前置依赖

- 当前无 CI/压测脚本，需在后续版本先落地：JaCoCo 覆盖率门禁（已接）、CI workflow（已加）、压测脚本与独立测试环境。
- P0 预约创建并发正确性依赖 #4 中的冲突原子化修复，未修复前该场景只做“缺陷复现”，不设通过阈值。
